# MateBook E Go 2023：macOS 移植研究

状态：**EXPERIMENTAL；E Go 硬件运行 NOT RUN；没有可刷入的 EFI 或 macOS 安装包。**

本分支的目标是让 MateBook E Go 2023（SC8280XP / Snapdragon 8cx Gen 3）
逐步具备本机运行 macOS 的能力，最终评估独立启动。当前交付是只读信息采集、
离线 CPU 能力解码和可复现的实验路线，不包含 E Go 的引导器或 GPU 驱动。
上游 README 中的桌面、内置 SSD 和 Adreno 加速结果属于 ASUS A16 / X2 Elite。

## 2. 为什么不能直接运行 A16 安装流程

固定基线的
[`probes/xnuboot/prepare.c`](https://github.com/MOON-DREAM-STARS/Snapintosh/blob/940eeb95ba637528dc45ba098e6b8091163dd489/probes/xnuboot/prepare.c)
存在以下实现要求：

| 要求 | 当前用途 | 移植方向与验收条件 |
| --- | --- | --- |
| RNDR / FEAT_RNG | 为 PAC domain 生成随机种子；失败返回 `-24` | 如实际缺失，设计可信熵源接口和生命周期；不能硬编码种子、用时钟替代或删除拒绝 |
| 地址 PAC | 当前 PAC domain、签名和认证路径 | 验证物理能力、KVM 暴露、五组 key 的上下文管理和 Apple 语义 |
| ECV / 时钟配置 | 当前客体计时器和宿主/客体频率处理；失败返回 `-15` | 评估采用宿主 timebase 的 VMAPPLE 路径；验证 deadline、单调性、中断、多 vCPU |
| VNCR / NV2 | 当前虚拟化后端 | 改用不依赖这一路径的 EL1 客体，或实现完整的旧架构后端；不是把一个 check 改为真 |
| A16 板级状态 | GPU、SMMU、时钟、中断、显示、NVMe 等 | 从 E Go 设备树/实际固件建立映射和所有权，不使用 A16 地址常量 |

上述要求描述当前实现。某项不满足不能推导为“任何方式都不能运行 macOS”。
相反，仅满足这些 ID 位也不能证明当前 monitor 能安全启动。

现有 `tools/probe-a16-cpus.py`、`probes/run.py`、`tools/cycle.py` 和页表探针依赖
q1n1、特定执行层级或 A16 硬件流程。本阶段不把它们包装成 E Go 的检测命令。

### 一个需要避免的解码错误

基线 `probes/run.py` 的 nested-virtualization 日志把 `ID_AA64MMFR4_EL1[27:24]`
当成 `NV_frac`。Linux 的公开系统寄存器定义将 `[27:24]` 定义为 `E2H0`，
`NV_frac` 位于 `[23:20]`。本分支的离线工具使用正确字段，并测试 E2H0 非零
不能制造 NV2 成功结果。当前改动不修改原有 monitor 或部署程序。

## 3. CPU 证据：保留采样环境

### 已发表的对照样本

[X13s 的裸机 Linux CPU 信息](https://github.com/hrw/arm-socs-table/blob/3aaecf1c158aa02ab6bf2eb9753b7a697b5867e4/cpuinfo-data/snapdragon-8cx-gen3)
中，A78C / X1C 的 `Features` 包含 `paca`、`pacg`。
[维护者说明](https://github.com/hrw/arm-socs-table/issues/15#issuecomment-1330436115)
区分了该裸机结果与不可靠的 WSL 样本。这里只引用其能力事实，不复制个人信息。

[VirtualBox 的 8cx Gen 3 CPU 报告](https://github.com/VirtualBox/virtualbox/blob/2f36df7749e6228e72bbcc675883a4b77b69f66a/src/VBox/VMM/VMMR3/cpus/ARM_Qualcomm_Snapdragon_8cx_Gen_3.h)
来自 Windows ARM 环境，记录了地址/通用 PAC、`SSBS=1`，以及未暴露的 RNDR、
ECV、NV。报告还把 stage-2 的几个粒度标为不可用。这是 **Windows 可见值**，
不能据此推断物理 CPU 没有相应 stage-2 页表支持。

本分支不包含上述 GPL 项目的源码拷贝，也不将其结果冒充 E Go 实测。

### 必须区分的层次

1. Arm 核心设计文档。
2. 固件/EL2 所暴露的硬件能力。
3. Linux 系统范围的安全特性交集及 EL0 过滤值。
4. KVM 给特定客体暴露的能力。
5. 实际指令、页表和 vCPU 切换实验。

Linux 的 [CPU feature-register ABI](https://github.com/torvalds/linux/blob/master/Documentation/arch/arm64/cpu-feature-registers.rst)
明确说明 EL0 的 `MRS` 可能返回过滤后的值。NV、TGran16、TGran16_2、TLBI range
等字段不能简单用用户态读到的零判为硬件缺失。`/proc/cpuinfo` 也不是每簇 CPU
未经处理的全部物理能力。

`TGran16_2=0` 表示 stage-2 的 16 KiB 能力沿用 `TGran16`；`1` 才表示该层级未提供，
`2` / `3` 表示相应支持。宿主 `getconf PAGE_SIZE` 与客体能否使用 16 KiB 页表是不同问题。
未知/保留编码必须保持未知，不能按“非零即支持”处理。

## 4. 第一阶段：只读采集

### Windows

在研究分支根目录运行：

```powershell
powershell -NoProfile -File .\tools\collect-ego-windows.ps1 -OutputPath .\build\ego-windows.json
```

该脚本收集产品型号、CPU 核数、内存、BIOS 版本、Windows build、TCB 组件版本与
SHA-256 等允许字段。它不读取序列号、账户、激活密钥、完整 PnP ID、固件转储或恢复密钥，
不修改启动设置。Secure Boot 查询若无权限则保留未知，不要求为此提权。

若系统策略阻止脚本，保留报错类型供后续处理；不要为第一阶段降低整机执行策略。
新输出文件不得覆盖现有文件。`build/` 已在仓库中，JSON 输出由 `.gitignore` 排除。
分享前仍应自己查看内容；诊断报告不应提交到公共仓库。

### 已经能运行的 Linux

```sh
python3 tools/collect-ego-linux.py --output build/ego-linux.json
```

该工具使用 Python 标准库，不启动外部程序、不下载文件、不写硬件，不加载模块。
它仅读取白名单系统信息并尝试 KVM 的查询接口，不创建 VM、不执行 `KVM_RUN`。
没有权限或文件缺失会单独报告；无需为一次信息采集改变 `/dev/kvm` 权限。

其中 CPU Features 是 **Linux 暴露的能力**；KVM capability 表示该内核提供的接口。
`KVM_CAP_ARM_EL2` 若被查询，表示嵌套 guest EL2 能力，不是宿主获得 EL2 的直接证明。
`/dev/kvm` 存在、API 查询成功或 capability 非零，都不等于 macOS 或测试客体已运行。

普通 gaokun 启动配置可能带有 `arm64.nopauth` 等规避参数。遇到 PAC 未暴露，
先核验参数及 EL2 流程；不要直接删除现有启动参数并宣称固件问题已经解决。

两个采集器的 JSON 是设备清单格式，与下一节的寄存器证据格式不同，不能直接互喂。

## 5. 离线寄存器解码

```sh
python3 tools/check-ego-capabilities.py --input build/ego-evidence.json --format text
```

该命令只解析已有 JSON，不会自行读取特权寄存器或连接目标机。输入 schema：

```json
{
  "schema_version": 1,
  "provenance": "linux_sanitized",
  "execution_el": 0,
  "registers": {
    "ID_AA64ISAR0_EL1": null,
    "ID_AA64ISAR1_EL1": null,
    "ID_AA64PFR1_EL1": null,
    "ID_AA64MMFR0_EL1": null,
    "ID_AA64MMFR2_EL1": null
  },
  "masked_fields": []
}
```

这是缺少观测值的格式示例，不是设备测试结果。省略或 `null` 必须保持未知。
`linux_sanitized` 会自动把 Linux ABI 不公开的相关字段保持为未知，即使输入非零。
工具接受 `raw_el2`、`uefi_el1`、`linux_sanitized`、`windows_visible`、`kvm_guest`、
`documentation`、`synthetic` 来源。`raw_el2` 必须来自确实处于该环境的已审查采样；
把 Windows 数据改标成 `raw_el2` 不会提高证据强度。

数字必须是 u64 整数或 `0x` 十六进制字符串，不接受任意额外字段。
输出区分报告中的编码、该采样环境是否提供能力以及仍需确认的物理/客体条件。
即便所有已知字段显示支持，后端状态仍为未完成硬件资格验证；不会输出刷机许可。
退出码成功只代表输入被正确处理，不能用作启动准入条件。

不要提交整份固件、ACPI/DT 转储、完整 dmesg 或命令行来填充该格式。

## 6. 选择验证路线

### 优先：Linux + KVM + Ventura VMAPPLE

这是验证 CPU 和 Apple 平台接口的路径，最终是否保留 Linux 宿主由实验结果决定。

- [gaokun](https://github.com/right-0903/linux-gaokun/blob/main/README.MD)
  提供设备适配经验；[slbounce](https://github.com/TravMurav/slbounce) 提供 EL2 交接方式。
- [W515y source bundle](https://github.com/DenrianWeiss/w515y-vmapple-scripts)
  有非 Apple ARM 上的 KVM / VMAPPLE 实践。其 KOS 内核偏移补丁不能加载到 E Go 内核。
- [Orchard](https://github.com/yaelliethy/orchard) 的 TCG 路径可作 CPU 模拟对照；
  该项目未把 ARM KVM 路径报告为实测成功。
- 初始目标选择匹配的 Ventura VMAPPLE 组件。其范围较小，但仍需要 PAC、16 KiB、
  hypercall、GIC、PSCI、时钟和部分指令适配；不假设它能在 8cx 上原样启动。

必须固定 XNU/内核集合、QEMU、Reims、Mesa、宿主内核和固件版本。
不要把各项目的最新分支混合后把启动失败归因于 CPU。

### 后续：独立 EL2 后端或 EL1 XNU

如 CPU 与 macOS 用户态已获得验证，再评估把宿主依赖逐项替换：
启动与内存所有权、GIC/计时器、存储、输入、网络、显示、GPU及电源管理。
Snapintosh 的 Apple 接口模型和图形前端可作参考；A16 的物理地址、NVMe 写入流程、
Adreno a8xx 命令和电源初始化不能移植时照搬。

当前 Linux/KVM 实验不是独立启动的完成证明。无 NV2 也不排除重新实现一个不同后端。

## 7. 已定位的具体研发任务

### 7.1 VMAPPLE 的 SSBS1 / SSBS2 条件

在 XNU `xnu-8796.141.3` 的固定 commit
`1b191cb58250d0705d8a51287127505aa4bc0789` 中：

- [`commpage.c`](https://github.com/apple-oss-distributions/xnu/blob/1b191cb58250d0705d8a51287127505aa4bc0789/osfmk/arm/commpage/commpage.c)
  把 SSBS 字段达到 1 作为设置 `gARM_FEAT_SSBS` 的条件。
- [`proc_reg.h`](https://github.com/apple-oss-distributions/xnu/blob/1b191cb58250d0705d8a51287127505aa4bc0789/osfmk/arm64/proc_reg.h)
  将该阈值定义为 `1ull << 4`。
- [`cswitch.s`](https://github.com/apple-oss-distributions/xnu/blob/1b191cb58250d0705d8a51287127505aa4bc0789/osfmk/arm64/cswitch.s)
  的 VMAPPLE 路径检查此 flag 后，执行需要 SSBS2 的直接 `MRS/MSR SSBS`。

**待验证假设**：如果 E Go 的 KVM 客体暴露 SSBS=1，该上下文切换路径可能执行客体
不支持的指令。应先在带同步异常向量的小型 EL1 客体中记录字段、PC、指令和异常，
再与实际使用的 kernelcache 比对。未匹配实际执行路径前，不发布二进制补丁偏移。

候选修改是单独检查 SSBS2 寄存器访问能力，并保留 SSBS1 状态语义。
不能简单把全局 SSBS 功能关闭就宣布修复。该源码条件在 Apple 原目标平台上的适用性，
与移植到不同 CPU 的条件是两回事。

### 7.2 TLBIRANGE、DIT 和用户态指令

[`tlb.h`](https://github.com/apple-oss-distributions/xnu/blob/1b191cb58250d0705d8a51287127505aa4bc0789/osfmk/arm64/tlb.h)
和 [`pmap.c`](https://github.com/apple-oss-distributions/xnu/blob/1b191cb58250d0705d8a51287127505aa4bc0789/osfmk/arm/pmap/pmap.c)
已经存在逐页或较宽范围的普通 TLBI 路径。可以评估复用，但仅关闭
`__ARM_RANGE_TLBI__` 不够：混合页的 `do_commpage_flush` 分支仍调用 range 形式。
需要覆盖 global/ASID、local/共享域、4K/16K 和 barrier 语义，并验证撤销映射、
重映射、权限改变和双 vCPU 不会留下旧翻译。TLBI 不允许直接 NOP。

`cswitch.s` 在 `__ARM_ARCH_8_4__` 分支还直接保存和恢复 DIT。必须核验选定构建是否
包含并执行这些指令；如果需要 guard，应与真实特性一致。软件跳过/模拟状态读写
不能提供硬件 DIT 的执行时间保证。

SHA3/SHA512 等在 commpage 中有运行时检测，可能让系统库选用其他实现；这不保证
所有预编译用户态都避开新指令。CPU 首次异常必须记录真实 opcode 和执行环境，
不能把普通算术指令 NOP，也不能把 QEMU 的 MMIO decoder 当成通用缺失指令模拟器。

### 7.3 A690 的 dma-buf-only 导入路径

固定审查版本：

| 组件 | commit |
| --- | --- |
| Reims | `2ce320931917e8a07a00243f53656f8cd11306b2` |
| metal2vulkan | `a2c440b8bcdcf20d34aa1694b61ae22c2a7ea68b` |
| Mesa 源码镜像 | `18879c94176c777064cbc5223a7206468c7a00a7` |

Reims 的
[`import.rs`](https://github.com/steelbrain/reims-vgpu/blob/2ce320931917e8a07a00243f53656f8cd11306b2/crates/reims-vgpu-vulkan/src/os/linux/import.rs)
已经把 `DmaBufSource` 传给 `HostMemory::with_dma_buf`。但是 metal2vulkan 的
[`Importer::new()`](https://github.com/steelbrain/metal2vulkan/blob/a2c440b8bcdcf20d34aa1694b61ae22c2a7ea68b/crates/metal2vulkan-runtime/src/host_memory.rs)
仍先要求 `VK_EXT_external_memory_host`，并用该扩展查询 host-pointer alignment。
[Turnip 扩展表](https://github.com/chaotic-cx/mesa-mirror/blob/18879c94176c777064cbc5223a7206468c7a00a7/src/freedreno/vulkan/tu_device.cc)
提供 dma-buf / external-memory-fd，未提供该 host-pointer 扩展。链接为 Mesa 代码镜像，
不是 Mesa 官方 GitHub 仓库。

因此现有 dma-buf 后备代码还不能证明 A690 已可用。首个实验应完全不带 macOS：

1. 创建小规模 sealed memfd，通过 `udmabuf` 导出同一批页面。
2. Vulkan 导入 fd，核对 memory-type bits、alignment 和资源要求。
3. CPU 写入 / GPU 校验，再 GPU 写入 / fence 完成 / CPU 校验。
4. 验证不连续区间、chunk 边界和 alias；明确缓存同步需求。

通过后再把 importer 分为 host-pointer 与 dma-buf 两条能力路径。不能只删除构造器
检查，否则后续仍会调用不存在的 host-pointer API。能力报告、alignment、memory type、
生命周期和无拷贝的同页语义必须一起满足。扩展名存在不是通过条件。

### 7.4 可构建基底的边界

W515y 的 source bundle 固定了 QEMU、Reims、metal2vulkan 和 shim 的版本，适合参考
匹配关系。四个 KOS/Kylin shim 依赖其专用内核；不要直接加载。Apple 启动路径还需要
真实的加密后端，不能用返回成功的 cipher stub 代替。启动实验应使用独立客体磁盘
overlay 与 AUX 副本，不依赖脚本注释中的“只读”承诺。

[Orchard 固定版本](https://github.com/yaelliethy/orchard/tree/c73a2bda1fd4afefd61204bb74afd74292ef2fe9)
的默认启动脚本使用 TCG。不能通过一个脚本不识别的 `ACCEL=kvm` 环境变量宣称切换了
硬件加速。其 HVC / NISV / PAC 初始化代码可作参考，必须独立核验 KVM 的实际退出原因
和 vCPU 状态。CPU 调试时也要确认图形初始化是否确实隔离，`-display none` 本身不保证。

## 8. 实验阶段与判定

| 阶段 | 交付及通过条件 | 当前状态 |
| --- | --- | --- |

| M7 设备整合 | 多核、输入、音频、电源、恢复路径；评估独立启动 | UNIMPLEMENTED / NOT RUN |

日志只保留必要且审查过的字段。一个阶段成功不能自动升级下一阶段状态。

## 9. 本分支的边界与验证

新工具只用于信息采集或离线分析，不被现有 `cycle.py` / monitor 构建自动调用。
它们不改变 A16 运行默认值、分区、固件、Secure Boot、DVFS 或系统策略。

可在普通开发机运行离线测试：

```sh
python3 tools/test-ego-capabilities.py
python3 tools/test-ego-collection.py
```

测试使用人工构造的数据与模拟设备接口，证明解码/过滤/错误处理，不证明 E Go 硬件支持。
PowerShell 运行验证、E Go EL2/KVM、Apple 内核构建与启动、Vulkan/GPU 实机验证需单独记录。
输出留在本地，且在公共提交中排除真实诊断数据。

涉及后续引导和存储实验时，应先保留 Windows 恢复方式与用户自己的恢复密钥。
实际分区、持久固件或时钟/电压操作属于另外的硬件实验，不由本只读研究分支授权。
